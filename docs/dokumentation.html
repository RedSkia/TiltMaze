TiltMaze – projektdokumentation

App-programmering – Cross-platform App Development 2026 · Marcus (enkeltvis) · .NET MAUI Blazor Hybrid + Supabase · Kode: se Git-repository

1. Problem og brugergruppe

Problem: Korte pauser i hverdagen mangler et hurtigt færdighedsspil, der bruger telefonens sensorer, og som er sjovere, når man kan måle sig mod andre. Top-lister i simple spil bliver hurtigt værdiløse, hvis nogen kan sende falske tider.

Løsning: TiltMaze er et labyrintspil set ovenfra. Man styrer en kugle ved at vippe telefonen eller trække en finger/mus på banen, undgår huller og når målet så hurtigt som muligt. Hver labyrint laves ud fra en sværhedsgrad og et seed, så “dagens labyrint” er ens for alle. Man ræser mod sit eget og andres bedste løb som spøgelser, samler mønter og køber udseende i en butik.

Brugergruppe: unge og voksne, der kan lide hurtige spil og at konkurrere. Platforme: Android (primær) og Windows.

Brugerkonti, data og roller

Hver spiller har en konto (brugernavn + kodeord, eller Google). Kontoen ejer sin profil og sine tider/spøgelser. Spillet virker også helt uden konto og uden net.

2. Design: skitser, navigation, theme, thumb zones, tilgængelighed

  • Layout: telefon i højformat: HUD øverst, banen fylder resten, bundmenu. Fra 768 px bredde skifter navigationen til en sidemenu, og siderne bruger to kolonner (fra 900 px). På tablet i landskab vises hele banen med sidepanel, fordi der er plads; kan banen ikke vises med mindst 40 px pr. celle, følger kameraet kuglen. Testet ved 390, 900 og 1400 px uden overlap.
  • Thumb zone: menuen ligger nederst; joysticket er flydende og kommer frem, hvor tommelfingeren trykker. Primære knapper (Play, Resume) er store og placeret nederst/centralt.
  • Trykmål: alt der kan trykkes er mindst 48 px (--touch) med mindst 8 px mellem naboer; afstande kun fra en 8-skala.
  • Theme via farvetokens: alle farver og afstande er CSS-variabler i app.css (--bg, --accent, --ball, --gold, --danger …). Designet er “Neon Arcade” (mørkt). Butikken har fire bane-temaer (Neon, Lava, Ice, Retro) der kun skifter variabler. Et lyst tema er ikke lavet endnu.
  • Tilgængelighed: fokus-ring på alt, dialoger med fokus på den sikre knap og Esc, resten af skærmen er inert; prefers-reduced-motion slår rystelse, konfetti og puls fra; fejl vises som tekst (ikke kun farve). Kontrast (4,5:1) og 200 % skriftstørrelse er ikke målt; skærmlæser-test er ikke lavet.

3. Arkitektur

  • Appen (client): .NET MAUI Blazor Hybrid. MAUI giver en rigtig Android/Windows-app med én skærm, der indeholder en BlazorWebView. Siderne (.razor) tegner UI; koden bag kører som almindelig .NET og kan bruge accelerometer, vibration, SecureStorage og fingeraftryk direkte.
  • Core: ren C# uden MAUI med al matematik (labyrint, fysik, kamera, spøgelse, belønninger). Testet med xUnit. Samme regler er porteret til TypeScript, så serveren kan afspille en tur.
  • Backend: Supabase – ingen egen server. Auth (konti), Postgres med Row Level Security, RPC-funktioner og én Edge Function (TypeScript/Deno).
  • Tredjepart: Supabase (hosting) og Google (valgfrit login, kun via Supabase).
  • Data og sync: Spillet er offline-først. Ny rekord gemmes i SQLite og lægges i en kø (PendingRun). RunQueue sender den ved start, efter login, ved ny rekord og når nettet kommer tilbage. Serveren svarer med pladsen på listen.

5. Sikkerhedsvalg

Login

  • Brugernavn + kodeord: brugernavnet bliver til e-mailen navn@tiltmaze.invalid (ingen bekræftelse, ingen persondata). Kodeordet sendes over HTTPS til Supabase Auth, der gemmer det som bcrypt-hash. Appen ser aldrig hashen.
  • Google: OAuth 2.0 + PKCE. Appen laver en tilfældig code verifier (32 bytes) og sender kun challenge = base64url(SHA-256). Login sker i en Custom Tab (Android) eller browseren (Windows). Appen får en engangskode tilbage og bytter den med verifieren til tokens. En stjålet kode kan ikke bruges uden verifieren.
  • Fingeraftryk/Windows Hello (valgfrit) låser kun det gemte login op på enheden. Passkeys er fravalgt (virker ikke i Android WebView uden meget native kode).

Tokens og lagring

  • Adgangstoken (JWT): kortlivet (Supabase-standard 1 time), holdes i hukommelsen og fornyes automatisk.
  • Refresh-token: gemmes i SecureStorage (Android Keystore / Windows) sammen med en udløbsdato; appen glemmer det efter 14 dage. Fornyelse sker med grant_type=refresh_token (Supabase roterer refresh-tokens). Log ud kalder serveren (scope=local) og rydder SecureStorage.
  • Øvrig data (tider, mønter, indstillinger) ligger i SQLite/Preferences og er ikke hemmelig.

Autorisation (ejerskab tjekkes på serveren)

create policy profiles_select_own on public.profiles
    for select to authenticated
    using (id = (select auth.uid()));   -- kun din egen række
  • Tabellerne profiles og runs har RLS. runs har ingen politik og ingen rettigheder: de kan kun nås via RPC’er, som selv slår brugeren op med auth.uid(). Ændrer man et id i et kald, ignorerer eller nægter serveren det.
  • submit_run kan kun kaldes af serveren. set_username og delete_me virker kun på den indloggedes egen konto.

Hemmeligheder og trafik

  • Kun den offentlige publishable key ligger i appen (sikker, fordi RLS og rettigheder bestemmer adgangen). Service-nøglen bruges kun i Edge Function. Ingen .env, kodeord eller nøgler i git.
  • Al trafik er HTTPS (https://…supabase.co). Android: allowBackup=false; kun MainActivity og Google-callback er exported; tilladelser kun INTERNET, ACCESS_NETWORK_STATE, VIBRATE og USE_BIOMETRIC.

7. Refleksion og arbejdsfordeling

  • Arbejdsfordeling: enkeltvis projekt. Jeg har valgt idé, krav, design og sikkerhedsprincipper, styret retningen og testet appen.
  • Forklaring af koden: for at kunne forklare al afleveret kode har jeg en studieguide (docs/TiltMaze-teknik-forklaret.pdf), DESIGN.md og slides med talenoter. Koden er kommenteret og holdt simpel med vilje.
  • Vigtigste valg: planen var et eget ASP.NET Core API i Docker. Jeg skiftede til Supabase, så jeg ikke selv skal drive og sikre en server, mens anti-snyd stadig kører som egen kode (Edge Function). Sikkerhed ligger i databasen (RLS + RPC’er), ikke i appen.
  • Udfordringer: samme labyrint i C# og TypeScript (løst med et eget seedet tilfældighedstal og tests mod facit); Google-login i Windows-app uden pakke (WebAuthenticator virker ikke, så appen lytter selv på en lokal adresse); Windows Defender blokerede WebView2-data på Skrivebordet.
  • Lærte: regler ét sted og testet; serveren stoler aldrig på klienten; sikkerhed designes ind fra start.
  • Næste skridt: lyst tema, kontrast- og skærmlæser-test, CI med secret-scanning, brugertest med flere personer, rotere service-nøglen.
